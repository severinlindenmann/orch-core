# Persisted formats: the CI guard

Every change to persisted data needs a migration step and a format bump (`packages/core/src/orch/migrate/steps.py`: `CURRENT`, `Registry`, `register`). `scripts/formats.py` enforces it per root kind (`host`, `workspace`, `hub`, `relay`, `publish`): it fingerprints what defines the kind's persisted format (SQLite DDL with comments stripped and whitespace collapsed, the version and schema constants and the `"v"` keys of persisted or signed JSON, the file and folder names of the data dir; the exact sources are the `RULES` in the script) and compares with `contracts/formats/<kind>.json`. Each package runs it from its own test suite (`tests/test_format_guard.py` in core, hub, relay and publish), so a change that touches one package fails that package's CI without core. To change a persisted format: (1) add the step, written inline as `register(Step("<kind>", <n>, <n+1>, "<name>", ...))` in `packages/core/src/orch/migrate/` (`steps.py` or a step module beside it; the guard finds it by reading those files, not by importing them); (2) bump `CURRENT["<kind>"]` to `<n+1>`; (3) run `python scripts/formats.py --update <kind>` from the repo root and commit the changed contract. `--update` refuses a changed fingerprint at an unchanged format, and a bumped format without its step; `--allow-same-format` is only for a change of `scripts/formats.py` itself (the extraction, never the data). Signed and append-only data (events, checkpoints, cards, revocations) must also be learned by the reader first (spec, "Data across updates"): a new shape in them is a bump of the kind that writes it, shipped in a release after the one whose readers accept it. Check by hand: `python scripts/formats.py --check [kind...]` (exit 1 and a message per problem).
