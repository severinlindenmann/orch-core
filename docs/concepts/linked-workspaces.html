Linked Workspaces

Several orch workspaces on one machine, or on another PC reachable over a VPN, hand tickets to each other. Your Internal workspace asks two customer workspaces for their part of the weekly report. Each one picks the request up, works it on its own data, and sends the result back. The Internal agent waits, then carries on.

The setup

Three workspaces, two machines, one person

Each workspace stays a normal orch workspace: its own repository, tickets, ledger and agents. A small listener next to orch serve watches for incoming handoffs. Workspaces only ever talk to peers you paired.

handoff: a request becomes a ticket over there result: released artifacts come back you, the human, with a separate ledger per workspace

A request is a ticket

A handoff lands as an ordinary backlog ticket in the receiving workspace, with requirements, acceptance criteria and its origin. The receiving agents work it like any other ticket.

The sender waits, it does not poll

The Internal ticket moves to waiting, blocked by the remote tickets. orch wait returns when every result is in, and the agent continues where it stopped.

Gates stay local

A peer never approves anything for another workspace. Auto-start and auto-release happen only under a charter you signed in the receiving workspace.

    Transport

    One message format, three ways to carry it

    A handoff is a signed JSON envelope. How it travels depends only on where the peer is. The receiving side runs the same checks in every case.

    Where the peer isCarrierHow it listensNotes
    Same machineSpool folder ~/.orch/peers/<name>/inboxFile watch, no network portSimplest case and the first to build. Outside every repository, so nothing reaches git.
    Same network or VPNHTTPS with pinned peer keysListener bound to the VPN address, for example 10.8.0.12:7710Works with Tailscale or WireGuard. Refuses any key you did not pair. Never binds to 0.0.0.0 by default.
    AnywhereTIX mailbox, sealed end to endDials out, as orch serve --remote already doesReuses the existing bridge, replay store and pairing. No open port on either side.

    The envelope, the peer list and the charter

    Handoff envelope

    Sent by orch handoff send. The hash binds the exact request text, like gate hashes do today.

    {
  "orch_handoff": 1,
  "id": "h_01JA7Q3M9V",
  "kind": "request",
  "from": { "workspace": "internal", "ticket": "INT-0142" },
  "to": "acme",
  "template": "weekly-report",
  "title": "Weekly report KW41",
  "requirements": "Deploys, incidents, open PRs, 30 Sep to 6 Oct",
  "acceptance": ["report.md in the agreed layout", "kpis.json"],
  "reply_by": "2026-10-09T16:00Z",
  "hash": "sha256:4be1…",
  "sig": "ed25519:9f3c…"
}

    Result envelope

    Sent only after release. It lists exactly the files that leave, each with its hash; they arrive as artifacts on INT-0142.

    {
  "orch_handoff": 1,
  "id": "h_01JA7Q3M9V",
  "kind": "result",
  "from": { "workspace": "acme", "ticket": "ACME-0311" },
  "outcome": "delivered",  // or declined, partial
  "summary": "12 deploys, 1 incident (P3), 7 open PRs",
  "artifacts": [
    { "name": "report.md", "sha256": "a91c…" },
    { "name": "kpis.json", "sha256": "07de…" }
  ],
  "released": { "by": "charter", "at": "2026-10-06T10:12Z" },
  "sig": "ed25519:c2a0…"
}

    orchestrator/peers.json names peers and transports. Keys live outside the repository, beside the ledger.

    Charter (ACME, signed by you)

    Lets one peer's requests of one template start and release without asking. Anything outside it lands on Today.

    # in the ACME workspace, your own terminal
orch peer charter internal \
  --template weekly-report \
  --max-size s --read-only \
  --auto-start --auto-release \
  --release-paths "reports/**" \
  --expires 2026-12-31
    CLI sketch

    New commands

    CommandWhoWhat it does
    orch peer pair <name>YouExchange keys with another workspace (a code shown on one side, typed on the other).
    orch peer listenYouRun the listener. Also part of orch serve --peers.
    orch peer charterYouSign which requests from a peer may auto-start and auto-release.
    orch handoff send <id> --to …AgentSend a request, add the remote tickets to blocked_by, move the ticket to waiting.
    orch handoff listAgentOpen handoffs in both directions, with remote status.
    orch handoff release <id>YouReview and send the result package back when no charter covers it.
    orch wait <id>AgentExists today. Also returns when the last handoff result arrives.
    Guardrails

    What keeps customers apart and you in charge

    • No remote decisions. A peer can file a ticket and send a result. It cannot approve, answer, release or give a verdict in another workspace. Each workspace keeps its own ledger.
    • Customers never see each other. Fan-out happens in Internal. ACME gets only its envelope and has no idea Globex exists; peers do not relay to third peers.
    • Only released bytes leave. The release shows every file and hash going out. A charter can limit release to paths such as reports/** and runs a secret scan first.
    • Requests are data. Text from a peer is treated like an external issue: the receiving agent reads it, it does not follow it as instructions. The guard hook and a read-only charter still apply.
    • No loops. A ticket that came in as a handoff cannot send handoffs of its own, unless you allow a depth of 2.
    • Nothing gets lost. The outbox retries while a peer is offline, the handoff id makes delivery idempotent, and a missed reply_by becomes a card on your Today.
    Plan

    Build it in four phases

    Phase 1

    Same machine, manual start

    • Spool transport and pairing
    • handoff send, inbox tickets, results as artifacts
    • orch wait covers handoffs
    Phase 2

    Charters and auto-start

    • Signed charters per peer and template
    • Runner starts agents in Terminals (tmux)
    • Release gate with path limits
    Phase 3

    VPN and the Peers page

    • HTTPS listener with pinned keys
    • Peers page, handoff chips on cards
    • Questions travel up to the requester
    Phase 4

    Relay and recurring work

    • TIX relay for peers off the network
    • Recurring handoffs: every Monday 08:00
    • Reports on peer lead times
    Open questions

    To decide before building

    • Who answers a question a customer agent cannot settle?Proposal: it goes up to the requesting ticket; the Internal agent answers when its own approved requirements cover it, otherwise you do.
    • Release by default, or charter only?Proposal: every result needs your release until you sign a charter for that peer and template.
    • One listener per workspace, or one per machine?One daemon serving all workspaces on a laptop is lighter; one per workspace keeps the isolation simpler to reason about.
    • Can a customer workspace send requests upward?For example "Internal, please review this PR". Same mechanism in reverse, off until you allow it per peer.
