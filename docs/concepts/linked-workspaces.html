Linked Workspaces

Orch workspaces hand tickets to each other, wherever each one runs: the same machine, another PC, behind a VPN or across a relay. Your Internal workspace asks two customer workspaces for their part of the weekly report. Each one picks the request up, works it on its own data, and sends the result back. The Internal agent waits, then carries on.

The setup

Three workspaces, one listener each

Each workspace stays a normal orch workspace: its own repository, tickets, ledger and agents. Every workspace runs its own listener next to orch serve. A workspace knows its peers only by name and address, never by where they run, so the placement below is just one example. Workspaces only ever talk to peers you paired.

handoff: a request becomes a ticket over there result: artifacts released under a charter come back you, the human, with a separate ledger per workspace

A request is a ticket

A handoff lands as an ordinary backlog ticket in the receiving workspace, with requirements, acceptance criteria and its origin. The receiving agents work it like any other ticket.

The sender waits, it does not poll

The Internal ticket moves to waiting, blocked by the remote tickets. orch wait returns when every result is in, and the agent continues where it stopped.

Gates stay local

A peer never approves anything for another workspace. Nothing starts on its own and nothing leaves a workspace without a charter you signed in that workspace.

    Transport

    One listener per workspace, any way to reach it

    We cannot know where a peer runs: the same laptop, another office PC, a VM, behind a VPN. So each workspace runs exactly one listener of its own and publishes an address when you pair it. The sender picks the carrier from that address; the envelope and the checks on arrival are the same for all of them.

    Peer addressCarrierHow it listensNotes
    spool:Spool folder ~/.orch/peers/<name>/inboxFile watch, no network portSimplest case and the first to build. Outside every repository, so nothing reaches git.
    https://HTTPS with pinned peer keysListener bound to the VPN address, for example 10.8.0.12:7710Works with Tailscale or WireGuard. Refuses any key you did not pair. Never binds to 0.0.0.0 by default.
    tix:TIX mailbox, sealed end to endDials out, as orch serve --remote already doesReuses the existing bridge, replay store and pairing. No open port on either side.

    Charters (signed by you)

    A charter is the only way a result can leave. No charter, no release: the request waits on Today until you sign one or decline. Upward requests need one too, on the receiving side.

    # in the ACME workspace, your own terminal
orch peer charter internal \
  --template weekly-report \
  --max-size s --read-only \
  --auto-start \
  --release-paths "reports/**" \
  --expires 2026-12-31

# in Internal: ACME may ask for reviews
orch peer charter acme \
  --template pr-review --max-size s
    CLI sketch

    New commands

    CommandWhoWhat it does
    orch peer pair <name>YouExchange keys with another workspace (a code shown on one side, typed on the other).
    orch peer listenYouRun this workspace's own listener. Also part of orch serve --peers.
    orch peer charterYouSign which requests a peer may send here, whether they start on their own, and what may be released back.
    orch handoff send <id> --to …AgentSend a request, add the remote tickets to blocked_by, move the ticket to waiting.
    orch handoff listAgentOpen handoffs in both directions, with remote status.
    orch handoff answer <id>AgentThe requesting agent answers a question a peer sent back up.
    orch wait <id>AgentExists today. Also returns when the last handoff result arrives.
    Guardrails

    What keeps customers apart and you in charge

    • No remote decisions. A peer can file a ticket and send a result. It cannot approve, answer, release or give a verdict in another workspace. Each workspace keeps its own ledger.
    • Customers never see each other. Fan-out happens in Internal. ACME gets only its envelope and has no idea Globex exists; peers do not relay to third peers.
    • Both directions, only when allowed. A customer workspace can send requests to Internal too, but only for templates a charter in Internal allows from that peer. Without one, the request is refused on arrival.
    • Nothing leaves without a charter. A result is released only under a charter you signed in that workspace, limited to paths such as reports/**, after a secret scan. Every file and hash going out is logged.
    • Requests are data. Text from a peer is treated like an external issue: the receiving agent reads it, it does not follow it as instructions. The guard hook and a read-only charter still apply.
    • No loops. A ticket that came in as a handoff cannot send handoffs of its own, unless you allow a depth of 2.
    • Nothing gets lost. The outbox retries while a peer is offline, the handoff id makes delivery idempotent, and a missed reply_by becomes a card on your Today.
    Plan

    Build it in four phases

    Phase 1

    Listener and handoffs

    • One listener per workspace, pairing, spool carrier
    • handoff send, inbox tickets, results as artifacts
    • orch wait covers handoffs
    Phase 2

    Charters and auto-start

    • Signed charters per peer and template
    • Runner starts agents in Terminals (tmux)
    • Charter-only release with path limits
    Phase 3

    Network peers and the Peers page

    • HTTPS listener with pinned keys
    • Peers page, handoff chips on cards
    • Questions go to the requesting agent
    • Upward requests under a charter
    Phase 4

    Relay and recurring work

    • TIX relay for peers off the network
    • Recurring handoffs: every Monday 08:00
    • Reports on peer lead times
    Decisions

    Settled

    • Who answers a question a customer agent cannot settle?The agent that sent the request. It is blocked in orch wait on the parent ticket, wakes, answers from its approved requirements and goes back to waiting. It asks you only when its requirements do not cover the question.
    • When can a result leave a workspace?Only under a charter signed in that workspace. Without one the request waits on Today until you sign a charter or decline it.
    • One listener per workspace, or one per machine?One per workspace. We cannot know whether peers share a machine, sit on a VPN or somewhere else, so each workspace is reachable on its own.
    • Can a customer workspace send requests to Internal?Yes, when a charter in Internal allows that peer and template. Otherwise the request is refused on arrival.
    Open questions

    Still to decide

    • What if the requesting agent's session has ended?Proposal: the question or result restarts an agent on the parent ticket through Start agent, the same way the Terminals addon starts one today.
    • What happens to a request that waits for a charter too long?Proposal: the sender sees it on its card after reply_by and can resend, wait or drop that part.
