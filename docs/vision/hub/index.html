One hub every workspace goes through

Each team or person has an orch workspace, running orch core, with its own keys. Workspaces no longer talk to the relay, publish or each other directly: everything goes through the company's one orch hub, its own component inside the company network. The hub holds the users and groups (or the Entra connection), decides which group may read, edit or admin which workspace, and is where admins work. There is no separate admin console.

Names orch workspace = a team's or person's space orch core = the software in a workspace orch hub = the company's control panel orch-relay · orch-publish = edge
Principle · D79 orch core always works standalone. One workspace on its own, with tickets, agents, skills, Mission Control and local signing, needs none of the hub, relay, publish or phone. Everything on this page is an addition, never a dependency.

Topology

Same three zones as the enterprise picture. What's new: the hub sits between the workspaces and everything else, and the admin console moves into it. Without a hub, a workspace still runs on its own, locally.

end-to-end encrypted release to the outside (human-approved) sign-in / identity slice shared into a shared space

Between companies: hub to hub, through the relay

One hub per company. Two companies, or two subsidiaries of one group, link their hubs. The traffic always goes through a relay, so neither side opens its network to the other. Each hub decides which of its workspaces and shared spaces the other side sees.

What changes against the v2 spec today

Today (orch-v2.md)
  • Each workspace host dials orch-relay itself (ws→ws mailboxes, push, drop).
  • Each workspace signs its own requests to orch-publish with its WSK.
  • The relay's directory holds accounts, devices, cards, memberships.
  • A person adds each workspace to the phone separately (QR per workspace).
  • Admin work lives nowhere yet; the enterprise picture has a separate admin console on the edge.
  • Shared spaces are a Drop space kind on the relay, key SK.
Proposed (hub)
  • Workspaces talk only to the hub. The hub, its own component, holds the one relay link and the one publish link.
  • Publish trusts the hub; the hub forwards a release only with the signature of a workspace admin on it.
  • The hub holds the users and groups (local, or synced from Entra ID) and the workspace cards. The relay keeps only routing ids.
  • Access is per group per workspace: read, edit or admin. Workspace admin replaces "owner". hub-admin manages every workspace.
  • People reach orch through channels on the hub: phone today, later Slack and others. The QR scan pairs with the hub, once.
  • The hub holds each user's signing key, bound to that user. A decision from any channel is signed by the hub for that user.
  • The admin console is part of the hub.
  • Shared spaces live on the hub; the hub can read them (option B), never the workspaces' own data.
  • Without a hub, a workspace is local only: no phone, no publish, no links to other workspaces.
  • One hub per company; companies or subsidiaries link hub to hub through a relay.
  • Selective join for personal workspaces: the hub never gets the workspace key and sees only items the owner shares.
  • Every signature needs a fresh tap on the phone or a passkey; sessions and Slack only show and route.

What can the hub read? Decided: trusted hub, selective join for personal workspaces

The hub becomes the most valuable box in the company. How much it can read decides how bad a break-in, or a careless admin, would be. Three ways to cut it:

Consequence of decisions 1 + 2

The hub holds every user's signing key, and hub admins manage every workspace. So the hub can act as any user, and through a user with read access it can open that workspace. Workspace data is still sealed in storage and on the wire, but the hub is a trusted operator, like Okta or Slack in a company, not a blind relay. The edge relay stays blind. What to protect: the hub server, its key store (HSM / keychain) and the hub-admin group; every action the hub signs goes in an audit log the workspace can check.

Full mode · team workspaces

Hub is a member

The workspace seals its key to the hub. The hub renders content for phone and browser and signs for users. Hub admins manage it.

Selective mode · personal (D80)

Hub sees only what you share

No workspace key for the hub. The owner picks ticket types, single tickets or tags; default is only needs-you summaries. Only the owner, at the workspace's terminal, can switch to full mode. Hub admins get no role.

Signing (D72, D81)

A fresh tap for every signature

The hub holds the user's key, but signs only after a tap on the phone (Secure Enclave) or a browser passkey. Local Mission Control and Slack hand off to that tap.

Safety nets from the Opus review
  • The hub signs only events it builds itself, bound to one workspace; a workspace host can never ask the hub to sign.
  • Two-level hub key: an offline root certifies the online key, which can be revoked and replaced without re-pinning.
  • Each workspace owner keeps an emergency key: leave the hub, rotate; pointing at a rebuilt hub needs the recovery code.
  • Publish accepts the hub only with a binding signed by the workspace itself.
  • Hash-chained audit log that every workspace confirms on sync.

The three options considered:

A · blind hub

Routes and manages, reads nothing

Like the relay today, but inside the company: access, directory, routing, policy. Content stays sealed between workspaces.

Keeps the E2E promise and the current protocol
No hub agents over shared context; shared spaces need their own key holders
B · decided 22 Oct

Blind for workspaces, member of shared spaces

Workspace-to-workspace traffic stays sealed. The hub holds keys only for the shared spaces it hosts and for its own admin data, so it can run agents on what teams chose to share. Each shared space shows "hub can read" on its card.

Context in shared spaces is usable; private workspace data stays private
A hub break-in exposes every shared space; needs a spec amendment for shared-space keys
C · trusted hub

Hub holds every workspace key

Full management platform: the hub can read, search and act in all workspaces.

Simplest admin story, cross-company search
Ends E2E between workspaces; reopens D2/D3 (keys only in each host)

Decided 22 Oct

  1. Names: orch workspace (runs orch core), orch hub, orch-relay, orch-publish.
  2. What the hub reads: B. Workspace traffic stays sealed end to end; the hub can read the shared spaces it hosts.
  3. Component: the hub is its own component, not a workspace with an add-on.
  4. Access: groups per workspace with read / edit / admin; people are added to groups on the hub. Admin = today's owner.
  5. Hub admin: members of the hub-admin group manage every full-mode workspace (for now).
  6. Signatures: the hub holds each user's signing key, bound to that user, and signs for them.
  7. Entra ID: not now, a must later. Groups live on the hub; later they sync.
  8. Channels: phone, later Slack and others, all through the hub. The QR scan pairs with the hub.
  9. Solo: without a hub, no phone and no publish.
  10. Several hubs: one per company; hub to hub through a relay, also between subsidiaries. No direct access to another company's workspaces.
  11. Hub down: workspaces keep working locally; phone, publish and handoffs wait. No second instance needed.
  12. Standalone (D79): orch core always works alone; the hub is never a dependency.
  13. Selective join (D80): personal workspaces may join and choose what to share.
  14. Local Mission Control (D81): hands signing to the phone or a passkey.
  15. Hub agents: later.

Still open (not blocking)

  1. Workspace veto on hub-admin grants, before the first real company.
  2. Small-team hub on the same machine as the workspaces, or always a separate host?
