ORCH CORE V3 · concept draft · 22 Oct 2026

Add-on marketplace

Three shelves, one install path. The tech-agnostic add-ons ship built in. Everything tied to a specific tool (GitHub, Jira, Slack, …) comes from a marketplace: a plain git repo with a marketplace.json index. Anyone can publish one (their own GitHub repo), any owner can add it. Whatever the source, the add-on lands through the same gate we already have: the package is read once, its digest is pinned, the owner sees what it may do and signs the grant.

built in · ships with orch core official marketplace · orch-maintained community / company marketplaces · anyone hub · optional company allowlist

Draft for discussion. Builds on what exists: orch.addon/2 manifest, package_sha256 digest, signed addon.granted, out-of-process JSON-RPC runner (ticket-format §8.1, C9). Things marked NEW don't exist yet.

1 · What goes where

Three shelves

Rule of thumb: if it only needs orch itself (tickets, agents, the workspace folder), it's built in. If it talks to a specific outside product or encodes one team's workflow, it's a marketplace add-on.

built in

Ships inside orch core

Tech-agnostic, maintained with the core, versioned with it. Still opt-in: installed with one click, still granted by the owner.

  • Dashboard, Start agent, Terminals, Worktrees
  • Wiki, Widgets, Schedules (+ follow-up)
  • Explorer, Usage, Estimate, Model routing
  • Quick tasks, Activity, Publish
Source: orch.addons/manifests/* in the wheel · no download
official marketplace

orch-maintained, tool-specific

Our own repo orch-marketplace, preinstalled as a trusted marketplace. Same rules as any other marketplace; we just sign it.

  • GitHub, GitLab, Landing (git host)
  • Linear, Jira
  • Slack, Teams (channels via hub)
  • Sentry, Vercel, …
Source: github:severinlindenmann/orch-marketplace · signed index
community / company

Bring your own

Any git repo. A person publishes one add-on, a company publishes its internal set, a community curates a list.

  • acme/orch-market — ACME's internal add-ons
  • jane/orch-addon-standup — a single repo, no marketplace
  • ./my-addon — local folder while developing
Source: added by an owner · or allowed by the hub admin
2 · How it fits together

Sources → one gate → the workspace

A marketplace never runs anything. It only tells orch where a package is and which bytes to expect. The trust decision stays with the workspace owner's signature.

ADD-ON REPO · github.com/acme/orch-addon-changelog
orch-addon-changelog/
├── orch-addon.json     # the manifest (required, at the top)
├── changelog.py        # the entry point
├── ui/                 # optional: dashboard tab (needs serve_http)
│   └── index.html
├── tests/
│   └── test_changelog.py
├── README.md           # shown on the marketplace card
└── LICENSE
├── pyproject.toml + uv.lock   # optional: deps, hashes pinned, in the digest
# no .so/.pyc/.dylib: the owner must be able to read every file
# deps are installed by the host at grant time, not shipped in the package
# caps: 256 files, 4 MB per file, 16 MB total
orch-addon.json
{
  "schema": "orch.addon/2",
  "name": "changelog",
  "version": "0.3.1",
  "title": "Changelog",
  "entry": { "cmd": ["python3", "changelog.py"] },
  "capabilities": [],            // none = "no extra permissions"
  "fields": {
    "line": { "type": "string", "max_len": 200,
              "set_by": ["addon", "member"] },
    "skip": { "type": "string", "max_len": 40,
              "set_by": ["member"] }
  },
  "agents_md": "Changelog: the field changelog.line is the
    user-facing summary of a finished feature. Keep it one sentence."
}
changelog.py · the whole add-on
"""orch add-on: one JSON-RPC request on stdin, one response on stdout.
The host sends only the ticket's key, type, status and this add-on's
own fields. The add-on holds no key; it *proposes*, the host checks
the proposal against the grant and signs it itself."""
import json, sys

def propose(p):
    t = p["ticket"]
    f = t["fields"]
    if t["type"] != "feature" or t["status"] != "done":
        return {}                       # nothing to propose
    if f.get("line") or f.get("skip"):
        return {}
    return {"set": {"line": f"Shipped {t['key']}."}}

req = json.loads(sys.stdin.readline())
if req["method"] == "propose":
    out = {"jsonrpc": "2.0", "id": req["id"],
           "result": propose(req["params"])}
else:
    out = {"jsonrpc": "2.0", "id": req["id"],
           "error": {"code": -32601, "message": "no such method"}}
sys.stdout.write(json.dumps(out) + "\n")
what the host sends (today's runner, unchanged)
{"jsonrpc":"2.0","id":1,"method":"propose",
 "params":{"addon":"changelog","version":"0.3.1",
  "capabilities":[],"trigger":"ticket.status",
  "ticket":{"key":"WEB-42","type":"feature",
            "status":"done","fields":{}}}}

An add-on may only return set (its own fields), sections (its own sections) and artifacts (its own kinds). Anything else is refused by Registry.check_proposal.

The index is a claim; the host re-checks every value against the fetched bytes. A lying index can only make the install fail, never install other code.

# authors
orch addon new changelog                    # NEW · scaffold
orch addon pack                             # NEW · validate + digest

Agents can browse and suggest, never install. market add, install, grant, update are human-only with user presence; mandates already exclude add-ons (D62). An agent can open a ticket “please install Jira” and the owner clicks.

6 · For the owner

Owner decisions · 22 Oct 2026

  1. GitHub and Landing move out of built-in into the official marketplace repo orch-marketplace. They stay one click away.
  2. Marketplace = plain git repo + marketplace.json. No hosted registry; a hub copy can come later.
  3. Dependencies are allowed from v1: lockfiles (uv.lock, package-lock.json, …) and other runtimes. The lockfile is part of the package digest and must pin hashes; the host installs the dependencies once, at grant time, into the add-on's own environment (network only during that step), and the review screen lists them. Detail to design: which package managers in v1, and how a dependency update is shown.
  4. Outside (community) marketplaces only after per-add-on OS-user isolation. Official + own company marketplaces first.
  5. With a hub, workspaces use only hub-allowed marketplaces.
  6. Publisher signatures optional, key remembered on first use, warning if it changes.
