# Refine a ticket

You turn a raw Ask into something the human can approve. You do not implement anything and you do not approve anything.

1. `orch show <id>`. If the human requested changes on the requirements, the Log holds their message: address it by editing the sections — only a section edit clears the request. Read the Ask and everything linked from it (external ticket, wiki page, screenshots in its artifacts). The Ask holds the tracker text when the ticket was imported, or the human's words; never edit it. Only an Ask you wrote yourself with `orch new` (no tracker key) may be cleaned up by you, and only until the requirements are approved: move requirements or criteria you put there into their sections, then `orch section set <id> Ask --file …`. Quote other relevant external text in `## Context`, in the language the source uses.
2. Explore read-only: code, data, docs. No edits outside the ticket, no commits.
3. Write the sections with `orch section set <id> <Section> --file orchestrator/temporary/<id>-<section>.md` (when you create the ticket: `orch new --requirements-file … --acceptance-file …`, or `## Requirements` / `## Acceptance criteria` headings in `--body-file`). The requirements gate checks these sections, not the Ask: it refuses while Requirements or Acceptance criteria are empty, and `orch new` / `orch section set` warn about it:
   - **Requirements** — what must be true afterwards, from the user's view.
   - **Summary** — one to three plain bullets for the human: what will be true afterwards.
   - **Acceptance criteria** — `- [ ]` checkboxes, each observable and testable. They are AC1, AC2, … in order: tasks reference them as `ac:1`, Verification lines as `AC1:`.
   - **Out of scope** — the tempting neighbours you will not touch.
   - Approaches with trade-offs go into `## Context` (say which you recommend and why); when the human must choose, ask it as a question with options instead. There is no Proposal section any more.
   - **Plan** — for a size with a plan gate (not `xs`), draft it now when the approach is clear: the approach, the files and repos it touches, the risks, how each criterion will be verified (prose or a numbered list, no checkboxes). The human then approves requirements and plan in one confirm ("Approve requirements and plan" on the dashboard and the phone) instead of being called back after an agent claims it. Leave it out only when the approach depends on an answer still open.
   - Do not create tasks; the agent that works on the ticket writes them after claiming it.
4. Ask now, during refinement, not mid-work: every open point that could stop the work later becomes a question, never an assumption: write `orchestrator/temporary/<id>-questions.yaml` and run `orch ask <id> --file ...` (format in the orch-tickets skill). Give each option its cost and set `recommended`. Use `blocking: false` only when the answer cannot change the requirements.
5. Size it. `xs` only for a change you could describe in one sentence (it skips the plan gate). A size listed in `gates.requirements_skip_sizes` (`orch rules` shows it; none by default) also skips the requirements gate: such a ticket needs no Requirements or Acceptance criteria, and the human moves it to `open` without approving. Size and type are part of the requirements approval: after it, only the human changes them. Keep open questions out of the Requirements, Acceptance criteria and Out of scope text (no line starting with "Open question", "Question for the human/you", or a bare "TBD" value): ask them with `orch ask`, or the human has to override it to approve. If it is bigger than a few days of work, propose splitting it and file the parts with `orch new --from <id>`, or, for a larger goal with several deliverables, propose an epic (`orch new --type epic`) and file the parts as its children (`orch new --epic <epic>`); the human then approves the epic and its children in one go. Whenever you create several related tickets, group them under an epic the same way, and refine every child (requirements, criteria, plan, questions) before you hand over, so the human reviews once.
6. `orch log <id> -m "refined: ..."` and `orch state <id> -m "..."`.
7. Hand over. Tell the user the ticket is ready for approval: requirements and plan together when you drafted the plan ("Approve requirements and plan" on the dashboard or the phone), else the requirements (`orch approve <id> requirements` in their terminal, or the dashboard); list the open questions with your recommendation for each. Then run `orch wait <id> --json` in the background; when it returns, `orch show <id> --json` tells you whether the requirements (and plan) were approved, sent back for changes or a question was answered; its `move` says whose turn it is now. Act on that, and wait again while the next step is still the human's. On timeout, run it again; stop waiting only when the user says so.

If the user answers in chat, ask them to record it with `orch answer` or in the dashboard. You cannot record answers for them.
