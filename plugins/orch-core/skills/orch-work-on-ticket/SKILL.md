# Work on a ticket

1. **Pick and claim.** `orch next` (or the ID the user gave), then `orch claim <id>`. Exit 4 means another session holds it: stop and tell the user. Read `orch show <id>` fully, especially the Ask, Current state (the handoff) and answered questions. Then run `orch task list <id> --json`. If it has tasks, you are resuming: continue with `next` (the doing task first) and skip step 2 unless the Plan no longer fits. No tasks, but the Plan has `- [ ]` checkboxes? Write them as tasks with `orch task add`; the Plan and its approval stay as they are. A plan approved together with the requirements (drafted during refinement), or a child of an approved epic, usually has its plan approved already: then write the tasks and go on (`orch task start` tells you if the plan still needs the human). Epics themselves are never claimed.
   - **A separate checkout?** Work in a git worktree created with `orch worktree add <id> --repo <repo> [--base <branch>]`, one per repo the ticket touches. It creates the branch from `git.branch_pattern` at `<root>/.claude/worktrees/<repo>/<slug>`, links branch and worktree to the ticket and links the workspace's harness files (skills, settings) into it, so `orch` and the factory runner work from there. Don't place worktrees elsewhere or symlink the whole `.claude` folder into one (a loop). `orch worktree remove <id> --repo <repo>` removes it again; the branch stays. A repo the ticket touches before any branch exists: `orch link <id> --repo <repo>`.
2. **Plan and task list.** If there are no tasks yet, this is your first job.
   - Before writing it, run `orch related <id> --path <file or folder you expect to touch>` (repeat `--path`). It lists done tickets that changed that code (read their Summary and Findings, and do not undo what was decided there), open tickets in the same files (say so in the Plan; suggest `blocked_by` to the user when the work collides) and files usually changed together with them (check whether they need the change too). It reads git history only, so it is safe at any time.
   - Write the Plan with `orch section set <id> Plan --file ...`: the approach, the files and repos you will touch, the risks, and how you will verify each acceptance criterion. Prose or a numbered list, no checkboxes.
   - Create the tasks in one call: `orch task add <id> --file orchestrator/temporary/<id>-tasks.yaml` (format in the orch-tickets skill). Each task is one verifiable change of roughly 1–4 hours. Give it `refs` to the files, artifacts, tickets or acceptance criteria (`ac:2`) it touches, a `verify` line when a command proves it, and `needs` when it must wait for another task. Put long notes into `orchestrator/static/<id>/…` and reference them with `static:` instead of writing them into the task text. Steps only the human can do get `owner: human`.
   - Then tell the user the plan and tasks are ready for `orch approve <id> plan` (`orch approve <id>` with no gate approves the one that waits; for a child of an epic, `orch approve <epic> plans` approves every waiting plan of that epic in one confirmation) and run `orch wait <id> --json` in the background (step 4 says how to handle what it returns). Until the plan is approved, `orch task start` and `orch task done` refuse (exit 5, "plan gate is pending"): that is the stop, not an error to work around. Open questions belong in `orch ask`, not in the Plan text: no line starting with "Open question", "Question for the human/you" or a bare "TBD" (see docs/ticket-schema.md), or the human has to override it to approve. For size `xs` there is no stop: create the tasks and go on. Every size needs at least one task.
3. **Work the tasks down, one at a time.** Run `orch task start <id> T<n>` before you touch anything for that task, and read its refs first. Only one task is in progress. When its verify line passes, run `orch task done <id> T<n> -m "<what proved it>"` right away; better, let orch prove it: `orch task done <id> T<n> --run` runs a verify line written as `cmd: <command>` or `check:<name>` (the project's configured check) itself, keeps a receipt and draws it in Verification. Don't batch ticks, and never tick a task whose tests fail or that is half done. Not needed after all? `orch task skip <id> T<n> -m "<reason>"`. Stuck on something outside your control? `orch task block <id> T<n> -m "<reason>" --on <Q3|ticket|T2>`, then go on with the next unblocked task. Found more work inside the approved Plan? `orch task add`. Work outside the Plan is a Plan change (step 5) or a follow-up ticket. Stay on the branch or worktree the customer skills describe, and record branches and PRs/MRs with `orch link` (`--pr 22` is enough when the workspace has one repo).
4. **Need a decision?** `orch ask` with a blocking question; the ticket moves to waiting, and orch blocks the task in progress on that question. Then run `orch wait <id> --json` in the background (the answer may come from the dashboard or a paired phone). Every wait result carries a `cursor` (text mode prints `cursor: N` on its last line): wait is read-only and remembers nothing, so chain it. Pass the last cursor as `orch wait <id> --after N --json` when you wait again without having written to the ticket since (a log, task or section change moves the default start past what you handled), and use `orch wait <id> --all --json` when several answers may have arrived: it returns every human decision since the cursor as `events` plus the highest `cursor`. When it returns, run `orch status <id>` (add `--json` to parse it: gates, questions with their answers, claim, tasks, `move`), read the answer and continue the task (orch has put it back in progress). If a task write is refused because your claim expired, `orch status <id>` says when, and `orch claim <id>` renews it. The same wait applies to every hand-off to the human: a plan or requirements approval, changes you made on request and a testing verdict. When it returns, `orch show <id> --json` says what the human decided, and its `move` (`who`, `kind`, `why`) says whose turn it is: the dashboard's own rule, so do not re-derive it. Questions you can foresee belong in refinement; ask mid-work only what the work itself uncovered. If it times out, run it again; stop waiting only when the user says so, and then tell them what you are waiting for. **In an AI Factory epic** (`orch epic show` says AI Factory) `orch ask` is refused: decide within the epic's text and record why with `orch log`, or leave the item out and list it as not built. Run one plain command per tool call (no `&&`, `;`, pipes, `2>&1` or `|| true`): a Dark run stops any such command for the human. A command denied with a request id (P-n) already has its request: do other work or `orch wait <id> --json`, then retry the exact same command, never a variant. Only a denial without a request id ("Denied by auto mode") needs `orch permit request "<command>" --ticket <id> --reason ...`; never file one for a command that was not denied (docs/factory.md).
5. **Plan no longer fits?** Update the Plan and the affected tasks, then ask the user to approve the plan again; their earlier approval is invalidated automatically. Do not keep working on an invalidated plan. Adding tasks that fit the approved plan needs no new approval. Changed Requirements or Acceptance criteria (for example a decision the human made in chat) invalidate the requirements approval: `orch task start` and the move to testing then refuse. Do not move the ticket back to backlog; ask the human to run `orch approve <id> requirements` (it shows what changed, keeps the status and the plan approval) and wait with `orch wait <id> --json`.
6. **Human tasks.** A task with `owner: human` belongs to the user: you cannot start, tick, skip or edit it. When your next task needs it, say so and point them to the ticket page, or to `orch task done <id> T<n> -m "..."` in their own terminal.
7. **Verify.** Check every acceptance criterion. Write one Verification line per criterion that names it, `- AC1: <what proved it> (<command or artifact>)`, with the real output indented below. Every file or URL that proves something goes in with `orch artifact add` — screenshots, reports, logs, dashboards, CI runs and PR checks — tied to its criterion: `orch artifact add <id> shot.png --ac 1 --inline --label "Jobs page lists 14 serverless jobs"` (writes the AC line with the image) or `orch artifact add <id> --url https://…/actions/runs/123 --kind build --label "CI run" --ac 2`. Show, not tell: a screenshot or a before/after image for a UI change, a small table instead of prose. Then tick the criteria you proved (a tick without a real `AC<n>` line is refused, also in a direct edit; `todo` or `TBD` is not evidence). **In an AI Factory epic** leave the Acceptance criteria as they are (a tick proves nothing there, and an edit of that section risks its approval): write the Verification with one top-level `- AC<n>: <what you checked and what you saw>` line per criterion into a file with your Write tool and set it with `orch section set <id> Verification --file <file>`, which replaces the whole section. The human's verdict view lists each criterion with your line.
   Reach for a widget at these moments (`orch widget add <id> --section <Section> --type <type> --data '<json>' --source "<command>"`, then `orch widget check <id>`; `orch widget show <type>` prints the shape):
   - Verification: a `checks` widget, one row per acceptance criterion (`AC<n>`, verdict `met`, `not_met` or `unproven`, the evidence).
   - A UI change: `screens` (one image per state) or `compare` (before and after), pinned from an artifact.
   - Measured numbers (sizes, timings, counts): `stats`, with the command that measured them in `source`.
   - Asking the human to choose (`orch ask`): an `options` widget in Context or Findings, the pick marked as recommended.
8. **Hand over** only when `orch task list <id>` shows every task done or skipped with a reason; `orch move <id> testing` refuses otherwise (exit 5 lists the open ones). Then run `orch state <id> -m "..."`, tell the user what to test and how, and run `orch wait <id> --json` in the background for the verdict (a send-back is step 10). Where quick tasks are on, `orch quick near <id>` lists the ones in the files you just changed: you may take them one at a time while you wait (orch-tickets skill, Quick tasks). The verdict is theirs. "Work on the ticket until done" means exactly this: every task closed, Verification filled, the ticket moved to testing.
9. **Changes requested?** If the human requested changes on the requirements or plan, update that section with `orch section set`. Only an edit of the section clears the request; a Log reply alone does not. Then tell the user it is ready to look at again and wait with `orch wait <id> --json` as in step 4.
10. **Sent back?** If the ticket returns from testing, read the human's note in the Log, add one task per point (`orch task add`), work them as in step 3, verify again and move it to testing again.

**Ending a session** with work left: keep the current task in progress (or block it with the reason), and write `orch state <id> -m "Doing T5: … Next: …"`. The next session resumes from `orch task list <id> --json`.

Commit and PR/MR rules are in AGENTS.md; `orch rules` shows whether you may commit, push or open a review in this workspace.
